# Android Tool Suite 产品与架构路线图

本文定义未来演进方向、依赖和验收条件，不记录任务进度或单次发布结果。规划不代表能力已经交付；实现边界以代码、契约和对应规范为准。

## 1. 产品定位

Android Tool Suite（ATS）是单一宿主中的个人工具平台：用户在主应用中安装、运行、备份和更新工具。普通插件使用统一声明式 UI 与平台无关 Capability 契约；需要宿主身份访问系统的能力使用签名、全信任的 `trusted-provider`。

运行时、AI 开发体验、发布平台和跨平台宿主分别演进。每条路线形成自己的可安装、可回退、可验证闭环，不把尚未验证的上层功能塞进底层运行时的验收条件。

## 2. 优先级与依赖

| 优先级 | 方向 | 启动或持续演进条件 | 边界 |
| --- | --- | --- | --- |
| P0 | 运行时可靠性、数据兼容与性能 | 随运行时和业务变化持续维护 | 不依赖 AI、社区或其他平台宿主 |
| P1 | AI 插件开发体验 | 清单、Capability、Dataset、任务与包签名契约稳定 | 不给模型隐式安装、签名或发布权限 |
| P2 | ATS 发布平台 | 签名与来源证明稳定，草稿可产出可审查构建 | 不用平台需求反向定义运行时协议 |
| P3 | 跨平台宿主 | Android 运行时稳定且存在真实非 Android 需求 | 不预设 Android 执行与分发模型可直接复用 |

依赖关系为 `运行时 > AI 开发 > 发布平台 > 跨平台`。上层可以提前研究契约和原型，但不能使底层发布依赖尚未验证的上层服务。

## 3. 运行时可靠性与性能

架构和兼容边界见 [运行时规范](../architecture/runtime.md) 与 [数据管理规范](../architecture/data-management.md)。演进重点包括：

- 持续覆盖 renderer 冷启动、旋转、前后台恢复、错误外壳、Provider 重连、权限撤销和任务恢复，避免只验证正常路径。
- 数据格式或恢复流程变化时，验证旧数据导出、空环境恢复、业务结果、失败回滚及明确的降级边界；不恢复旧 API1 执行路径。
- 建立基于实体设备的 Macrobenchmark 场景，覆盖冷启动、分页、长列表和插件页；保存 FrameTimingMetric、Perfetto trace、构建类型、温度与刷新率模式。
- 根据 trace 定位主线程 I/O、重复组件创建、重组、Pager 缓存和布局热点；不以刷新率浮层代替帧时序指标。
- 在可重复基线之上评估 Baseline Profile、R8 与资源压缩，并验证反射保留规则；性能证据作为 CI 或发布附件，不写入长期规范。

验收条件：指定场景能重复执行并定位回归；功能、权限和数据兼容不因优化而退化。模拟器用于验证脚本与交互，性能结论以目标实体设备为依据。

## 4. 可选执行后端

WASM、独立进程或更强隔离后端是可选演进方向，不是普通 Web/Worker 插件的入门门槛，也不能改变公开 Capability 和 Dataset 语义。

引入新后端前应验证包体积、启动成本、内存预算、超时可中断性、目标 Android API、设备引擎支持情况及崩溃影响范围。WASM/WIT 不暴露裸 Android 类型、任意文件系统、socket 或宿主内存。能力不支持时应明确拒绝或使用已定义的替代路径，不能以隐藏 WebView 模拟后台 Worker。

验收条件：同一契约 fixture 在不同后端得到一致结果；超时、撤权、崩溃和恢复行为可测。引擎选型与支持范围在实现前重新验证，不把历史候选调研当作可交付结论。

## 5. AI 插件开发体验

详细阶段、交付内容和批准边界见 [AI 插件开发计划](ai-plugin-development.md)。该方向依赖稳定运行时契约，目标是把自然语言需求转为可审查源码和可复现制品，再交给独立的安装或发布流程。

Developer Agent 与插件调用的 AI Provider 分别授权，不能把模型生成结果直接视为已批准安装或发布。

## 6. 发布平台

对象模型、可见性阶段和验收条件见 [发布平台计划](publication-platform.md)。该方向消费运行时包与签名契约，并接收开发流程产出的草稿；不反向为运行时增加社区、推荐或计费耦合。

GitHub 是源码、CI 和制品镜像 Adapter。平台演进应保持本地签名包、其他兼容索引及离线安装可用。

## 7. 跨平台宿主

公共清单、RPC、Capability、Dataset、任务和错误模型保持平台无关。目标平台实现必须独立评估插件分发、代码执行、后台任务、密钥保护和审核限制，不复用 Android APK 或动态 Native Provider 的可用性假设。

先验证契约兼容性和最小纵向工具，再决定是否建立 iOS、Desktop 或 KMP 产品工程。没有真实平台需求时只维护协议扩展点，不以空工程代表实现进度。

## 8. 演进验收原则

- 每条路线明确适用范围、依赖、退出条件、风险与回滚边界。
- 组件测试、包校验、数据兼容和 UI 规范按变更范围验证；跨仓库协议变化执行完整集成构建。
- 自动化、模拟器、实体设备安装与人工业务验收分别报告，不互相替代。
- 提交与发布遵循 [发布指南](../development/releasing.md)；产品变更记录在各组件更新日志，执行进度和验证结果留在任务、PR、CI 或发布附件中。
