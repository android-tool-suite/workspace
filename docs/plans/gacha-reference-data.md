# 游戏资料动态更新与抽卡精细分析计划

本文记录后续演进方向，重点是抽卡分析插件的公开游戏资料、原始记录保真和精细分布展示，以及宿主 Dataset、任务、权限和小部件缓存之间的协作。不代表以下能力已经实现，也不作为实时数据源状态看板。

实施时遵循 [运行时规范](../architecture/runtime.md)、[数据管理规范](../architecture/data-management.md) 与 [UI 设计规范](../design/ui-guidelines.md)。Phigros 的版本定数缓存与更新后重新核对可作为实现参照，不修改它的 RKS、存档或历史语义。

## 1. 问题现状与修改原因

以下是本方向的源码核对依据；对应实现发生变化时，应同步改写问题描述，不能将计划中的行为写成已交付能力。

| 问题现状 | 对用户的影响 | 修改原因与方向 |
| --- | --- | --- |
| 版本日历、历史 UP 卡池与常驻名单分别维护，主要随插件包更新；获取新抽卡记录不会刷新这些资料 | 日期可能能识别版本，但 UP 名单仍旧，资料覆盖终点之后的记录可能无法归类 | 将公开资料与程序版本解耦，统一维护来源、覆盖范围、修订和独立更新 |
| 原神内置历史将同一期的多个角色活动池合并成一个 UP 名单 | 可以辅助判断是否 UP，却不能直接表达“这一期某角色的独立卡池” | 保留同期开出的独立池及原始池类型，建立它们与版本、期次、UP ID 的关系 |
| 星铁内置历史按游戏卡池 ID 保存 UP ID，生成时未保留上游提供的开放时间 | 现有资料不足以直接建立完整期次排期和区域边界 | 保留上游时间字段，并与官方公告、版本日期及服务器规则交叉核对 |
| 本地兜底规则使用名称名单，未按版本生效；未命中常驻名单时会被当作 UP | 新增常驻角色、旧版本记录和不同语言名称可能导致误判，进而改变 UP 数量与平均 UP 抽数 | 以物品 ID、版本生效规则和明确证据判定；资料不足保留未知，不把“没找到”当作肯定结论 |
| UIGF 转换对布尔 false、数字 0 的扩展 UP 标记保留不完整，导出未保留该扩展标记；通常的获取与导入未保存版本扩展字段 | 导出再导入可能改变可用证据，算法支持读取扩展字段也不等于获取链路已保存它们 | 区分字段缺失与有效的假/零，保存来源与可用原始字段；标准导出遵守对应规范，完整备份保留扩展证据 |
| 现有记录合并按稳定记录 ID 跳过重复项，而不是补齐已有记录的缺失字段 | 即使重新获取的记录包含更多信息，也不保证旧记录能获得这些字段 | 单独设计字段补全与冲突处理，保留用户修订；不把“刷新全部记录”描述成已经补全全部信息 |
| 某些旧工具已丢失原始池类型或具体卡池 ID，时间也可能缺少时区/服务器信息 | 同期开着多个池时，三星或常驻出货无法证明用户选了哪个池 | 展示确定程度与歧义，允许只归类到版本/期次，不靠抽到的角色猜整段记录的卡池 |

## 2. 目标、范围与边界

目标是让用户无需等待插件发版，就能获得更完整、可追溯的版本、期次、卡池和 UP 资料，并看到这些资料如何影响统计。

本方向包括：

- 原神与星铁的版本边界、各期实际排期、独立卡池、UP 物品及常驻生效规则。
- 物品 ID、名称、语言和必要的显示资料；图片为可选增强，不阻断统计。
- 公共资料独立缓存与更新、资料覆盖查询、统计重新计算、小部件摘要失效。
- 原始记录字段保真、用户主动补全缺失信息，以及兼容旧导入与完整备份。
- “版本 → 期次 → 独立卡池”的分布、简要分析与明细导航。

边界是：

- 公共资料更新与用户原始记录获取是两个动作。更新资料不自动扫描游戏日志、读取登录凭据或获取私有历史。
- 不上传用户 UID、记录或凭据来换取公共卡池资料；公开源的读取只使用必要的公开参数。
- 不以该方向重启宿主整体性能基线或改造全部插件架构。先复用已有 Capability、Dataset 与任务机制；只有出现可复用的契约缺口时才评估公共 API 变更。
- 不承诺所有历史都能精确恢复。官方仍返回相应记录时可以主动重新获取；原始标识已丢失且无有效备份时，公共排期无法补回用户当年的选择。

## 3. 更全面的信息模型

以下是逻辑需求，不是已发布的数据格式或 SDK API。

| 对象 | 需要保存的信息 | 必须避免的混淆 |
| --- | --- | --- |
| 来源与资料修订 | 来源 ID/URL、采集时间、源修订、内容哈希、解析器/模式版本、地区与覆盖范围、校验结果 | 游戏版本、资料修订和插件版本分别表达；哈希用于一致性校验，不能代替来源可信性判断 |
| 游戏版本 | 正式版本标识与名称、公告引用、维护/开放边界及时间解释 | 日期只有一天精度时不能冒充精确开放时刻，也不能用某一期卡池结束时间代替完整版本结束 |
| 版本期次 | 所属版本、期次序号、实际开始/结束、服务器范围、显示标签 | 不按固定周期平分；有第三期时显示“第 3 期”，不强塞入上半/下半 |
| 独立卡池 | 游戏内卡池 ID（若有）、原始池类型、归档稳定 ID、公告 ID、卡池名称、开放区间、UP 物品 ID、地区及期次关联 | 游戏卡池 ID、公告 ID、人造历史条目 ID 是不同标识；星铁的 companion 字段也不能未经核验直接当作期次 |
| 物品与资格规则 | 物品 ID、多语言名称、类型/稀有度、常驻或活动资格的版本生效范围、公告证据 | 名字用于展示，ID 用于匹配；物品出现在字典里不等于已经实装、加入常驻或处于 UP |
| 玩家原始记录 | 原始 gacha_type、gacha_id/schedule_id（若提供）、item_id、记录 ID、当地时间、时区/服务器、来源明确提供的扩展标记 | uigf_gacha_type 的合并类别用于统计，不代替原始池类型；所有 ID 避免丢失精度 |
| 推导结果 | 版本/期次/卡池候选、UP/非 UP/未知、依据、所用资料修订、规则版本、手动覆盖 | 推导不覆盖原始记录；保留“唯一匹配”“仅能定位期次”“存在多个候选”“资料未覆盖”等差异 |

对长期联动池、集录池和其它特殊池，分别记录“活动的开放区间/初始所属版本”与“这次抽卡发生的版本”。不要求一张跨版本的池只能属于某个普通上半或下半。

### 4.3 不作为新在线依赖的来源

- [UIGF 旧 mihoyo-api-collect](https://github.com/UIGF-org/mihoyo-api-collect) 作为历史文档参考；其说明已指向新的 mihoyo-api-sdk，不当作接口持续维护的保证。
- [Caughtwind 历史 UP 接口说明](https://uigf.org/zh/mihoyo-api-collection/genshin_impact/thirdparty/historical_up_items.html) 与旧物品接口已被文档标为弃用；只用于发现历史资料或格式，不列入默认在线更新链路。
- 不把未经核对的镜像、第三方搬运脚本或搜索摘要当成独立权威来源；不同网站也可能搬运同一份上游，不能以“多站相同”代替真正的来源校验。

## 5. 动态更新、缓存与兼容方向

1. 统一为插件可读取的结构化资料包，保留各来源修订、地区和时间语义。远端 JavaScript/HTML 通过受控适配转换成数据，不 eval 远端代码，不执行第三方采集脚本。
2. 保留内置资料作为离线初始值；下载的资料使用独立 Dataset 保存，不与 mihoyo-session、record-links 或用户原始记录混在一起。采用内置资料、已校验缓存、无法确认则未知的回退顺序。
3. 先下载到候选代次，校验模式、ID、时间区间、关联完整性和哈希，再原子替换该游戏的有效快照。失败保留旧快照；不同游戏的部分成功分别报告，不把跨 Dataset 的多步写入说成统一事务。
4. 明确来源冲突的采用规则：官方已确认公告优先，社区资料补缺，用户校正单独标注。地区不同、公告修正和时间解释不同不能静默覆盖；冲突未解决时保留候选与未知状态。
5. 更新后重算适用版本/期次、UP 归属与统计，刷新相关主页摘要缓存。提供必要的变化说明，例如哪些资料覆盖补齐、哪些记录归属发生变化；不修改原始记录。
6. 保留有实际引用价值的旧资料修订，限制可再生成缓存容量；备份明确区分可重新下载缓存、用户人工校正和解释历史统计所需的修订引用。
7. 新数据项和恢复规则遵循宿主已有 Dataset 契约。旧备份没有资料缓存时仍可恢复原始记录；无法支持的新字段降级展示，不以修复资料为由要求删除账号。
8. 手动更新登记真实任务，按实际缓存提交结果标记成功/失败。自动检查保持安静、控制频率；不得阻塞本地浏览，也不将短时读取变成闪过的零值、占位摘要或新的等待页。

原始字段补全是另外一条流程：只有用户主动发起且原接口仍有记录时才重新读取；按记录稳定 ID 补充缺失字段，区分“没有值”与 false/0，保留修改来源及冲突。资料已丢失且没有可靠来源时，明确无法补全，不用附近某次五星给整段记录指定卡池。

## 6. 更全面的展示方向

- 设置一个所有账号共用的低频“游戏资料”入口，显示各游戏的来源、资料修订、更新时间、覆盖范围和更新结果；与当前账号的统计来源/人工规则设置区分开，不再占据分析首页顶行。
- 分布支持月份、版本、期次及独立卡池。普通两期可显示“上半/下半”，其它排期显示实际第 N 期或特殊池；常驻、新手、集录、千星奇域和联动池保留各自语义。
- 版本或期次分析显示真实起止、当前筛选、各卡池抽数、五星与已确认 UP/非 UP/未知数量，并提供票券/卡池占比、每日抽数和五星获取。平均 UP 抽数对资料缺口、未知归属与不完整历史的处理应明确可解释，不能靠排除失败记录让结果更好看。
- 原神的原始 301/400 或其它独立身份用于具体池匹配，共享保底的统计类别仍可合并；星铁优先使用具体 gacha_id。同类型同期开着多个池而无法唯一匹配时，显示“同期开池/无法区分”，不硬指定角色。
- 点按月份、版本、期次或卡池先进入同一范围的简要分析；原始明细继续位于更内层的更多菜单，返回保留来源、筛选和位置。不在各级页面重复完整账号摘要、资料管理与任务历史。
- 资料详情只展示帮助判断的来源、覆盖、证据和歧义。技术哈希/解析版本放在资料详情，主要分析页优先展示实际统计与简短说明。
- 无图片、字典缺名或网络失败时，保留 ID、已有名称和可用统计；不虚构角色、期次、UP 标记或抽卡结果。

## 7. 实施依赖与拆分顺序

| 阶段 | 目标与依赖 | 退出条件 |
| --- | --- | --- |
| 资料与字段模型 | 明确原始池身份、服务器时间、来源修订及资格生效规则；修复缺失值/false/0、扩展字段和重复记录补全语义 | 能解释已有记录的证据，无法唯一归属的记录保持歧义；新旧导入与备份保持兼容 |
| 动态更新与缓存 | 接入官方公告、历史排期和字典适配器；复用已有网络权限、Dataset 原子写入、任务与摘要失效机制 | 资料可独立更新、离线使用和失败回退；更新不覆盖用户原始记录与账号设置 |
| 精细统计与展示 | 在已核验资料与身份字段之上实现版本期次、独立卡池及简要分析 | 统计数值与相同筛选下的明细一致，来源与未知清晰，普通屏幕下主要操作路径简洁 |

不建立无数据支撑的“全部历史已精确恢复”里程碑，也不要求每个候选来源都接入。先选择字段可靠、覆盖明确的主源与有限补充源；覆盖不足以降低展示精度处理。

## 8. 验收条件

- 公共资料能独立更新；成功、无变化、网络失败、限流、解析格式改变、撤销权限和错误资料都不破坏最后可用缓存。
- 新旧资料有来源与修订可查，资料中的不同命名空间、时区和重复/重叠区间不会被错误合并；上游未正式确认或未覆盖的数据不被当成确定事实。
- 用合成记录覆盖原神双角色池、武器/集录/千星池、星铁并行角色/光锥/联动池、跨版本长期开池、多期版本和边界时刻；包括 UTC+8、UTC+0 及其它支持的时区，零偏移不能被默认成 +8。
- 同一 raw 记录的原始 gacha_type/gacha_id/item_id、扩展 UP 标记与时间证据经过保存、完整备份和兼容导入后保持一致；字段补全不重复增加抽数、不覆盖用户校正，冲突能被解释。
- 缺失池 ID、时间/地区不充分、多候选、资料未覆盖等情况不被判为精确卡池或肯定 UP；明确原始标记与用户覆盖的优先关系，保留来源。
- 所有分析、饼图、每日柱状图、五星列表与明细使用同一记录范围，更新后的摘要缓存及时失效；统计变化可以追溯到资料或规则的变化。
- 日常屏幕和默认字体下，更新入口、期次切换、更多明细与返回路径可直接使用；资料不可用时可继续浏览本地内容。非常规布局测试不反向削弱正常体验。
- 旧备份缺少资料项时可恢复记录并降级展示；插件更新、资料更新和用户主动记录补全分别验证，不互相替代。
- 实施时同步源码、声明的 Dataset/权限、组件 CHANGELOG、UI 规范与预览，并按实际变更范围执行组件或集成验证；模拟器验收、真机安装与用户手动验收分别说明。
