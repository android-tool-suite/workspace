# 分支与发布

外层工作区及六个组件仓库均以 `main` 为主分支。组件日常开发可以直接在各自的 `main` 上进行；需要隔离并行工作或单独评审时，再按需创建 `codex/*` 分支，不要求长期维护固定用途的开发分支。提交到 `main` 不等于发布，正式版由显式版本标签触发。

历史存档分支不参与日常集成，清理时按其保留目的单独判断。保留含未提交修改的工作树；删除工作树前检查其自身和全部嵌套仓库。组件分支独立管理，外层 gitlink 只在组件已经验证、提交并可从远端获取后更新。

外层 `main` 维护已验证的组件集成组合；单组件日常开发仍在对应仓库进行，不因直接使用组件 `main` 就同步更新外层 gitlink。

## 本地调试

组件 `ci.yml` 验证并上传 Actions 构建产物，不创建 Release。Debug 仅用于本地构建、模拟器和 ADB 实体设备调试；不维护远程 Debug 工作流、标签或调试目录。

跨仓库联调从工作区根目录执行：

```powershell
.\tools\build-all.ps1
.\tools\install-latest.ps1 -Serial <设备序列号>
```

单组件开发使用对应仓库的构建命令，只安装本次重新构建的产物。插件可通过 Debug ADB 入口同版本原子替换；本地构建和安装不算发布，不必为每次调试提升版本。

需要原生 SDK 和 ATS CLI 的 Provider 构建分别锁定两个来源：SDK 使用对应的公开版本标签，CLI 使用能够验证目标 Runtime Contract 的宿主提交。不得因为原生 SDK ABI 未变就沿用旧标签中不支持新清单的 CLI；推送依赖该 CLI 的插件前，先确保固定的宿主提交已在远端可获取。

## 正式版与 SDK

正式发布继续手动推送 `v<versionName>`，必须匹配构建版本。SDK 的 `plugin-sdk-v<version>` 标签标识相应 SDK 源码，供可信 Provider 的正式构建引用，不应触发应用发布。发布前核对版本、versionCode 与 CHANGELOG；Debug、预发布、正式发布均算发布。外层工作区不额外复制组件 Release。

GitHub Release 的 APK 与插件包附件名包含对应组件版本，例如 `android-tool-suite-v2.1.0.apk`、`phigros-advisor-v3.2.0.atsplugin`。准备发布脚本从已核验版本生成名称，同时写入 `release-metadata.json` 与 `SHA256SUMS.txt`；发布步骤按元数据上传该文件。用于本地构建与 ADB 安装的 `artifacts/` 固定名称保持可用，索引继续识别旧名称的历史 Release。

Release 正文直接提取对应版本 `CHANGELOG.md` 的二级标题及其内容，写入 `release-dist/release-notes.md`，通过 `gh release create --notes-file` 发布。只精确匹配一个版本段落，缺失、重复、空正文或仍标记“未发布”时拒绝发布；不使用自动生成说明，也不在发布时静默筛除日志条目。填写发布日期前先整理当前版本日志，只保留产品变化、兼容范围与升级说明，测试数量、验收结果、fixture、CI、分支、标签与仓库维护记录留在相应开发记录中。

正式发布完成后，各组件通过 GitHub App 向 `plugin-registry` 发送更新事件，由索引工作流生成并签名正式最新索引与历史目录。若通知失败，可手动运行该仓库的 `pages.yml`，无需重新创建 Release。

## 发布前核对

- 以对应组件的上一发布版本为比较基线，核实 versionName、versionCode、数据兼容声明和未发布更新日志；只整理待发布版本自身的内容，不合并不同未发布版本，也不删除中间版本的原记录。
- 保持当前 CHANGELOG 的版本划分，不把其中不同版本（包括未发布版本）的日志合并到一起；已经形成的历史合并结果保持原样，不重新拆分或恢复已合并的中间版本。
- 无法确认存在错误的历史日志按现有内容保留，不修改或追加核实状态说明；仅修正有明确源码或发布证据的问题，缺少标签或独立源码快照本身不构成修改理由。
- 逐提交检查 `git log -p -- CHANGELOG.md`，并结合上一发布标签至当前源码的差异核对中间迭代：保留最终产品变化，排除已经撤回的实现，防止整理新版时改写旧版或遗漏仍有效的变化。已发布版本段落以对应 `v<version>` 标签为基线；发布工作流用完整 Git 历史与标签自动核对所有旧段落。已核实的历史文案修正单独记录在组件 `.github/changelog-corrections.json`，绑定原标签提交、原文摘要、修正文案摘要和源码依据；标签或原文不符、修正文案再次变化，以及没有记录的旧段落改写都会阻止发布。
- 本地可先运行组件的 `.github/scripts/test-release-notes.ps1`，再 dot-source `release-notes.ps1` 调用 `Assert-ChangelogHistory -RepositoryRoot <组件目录> -CurrentVersion <待发布版本>`。历史事实错误须单独核对标签源码与发布记录；不通过新版日志整理覆盖旧版行为。旧 Release 正文可单独移除测试、验收与仓库过程信息，保留该版实际产品变化，修改前备份正文，修改后核对正文和附件清单；不移动标签、不重新上传附件。
- 按变更范围执行组件测试、包校验和集成构建，将最终源码、产物摘要与验证结果关联；不能以旧日志或旧构建清单代替当前结果。
- 权限、renderer、Provider、任务或数据恢复变化要覆盖相应生命周期与失败用例。旧数据导出、空环境恢复、业务读取、密码／损坏校验与降级边界按 [数据验收矩阵](../architecture/data-management.md#9-发布验收矩阵) 验证。
- 分别说明模拟器、实体设备安装与手动业务验收的覆盖范围。只有涉及性能结论时才要求目标设备的可重复测量；已有 performance 变体不代表已建立性能基准。
- 正式签名、宿主兼容范围、权限变化与升级注意事项核对后再发布。发布完成后验证实际附件名称、摘要及签名索引；组件发布不会自动更新外层 gitlink。
